# 5.10 Port — OPPO Reno11 Pro (PJJ110)

> Experimental first 5.10 port of the GhostLock (CVE-2026-43499) exploit family.
> Status: **root cause identified via upstream fix; pi_waiters write path dead; dangling pi_blocked_on hypothesis pending** (2026-08-19).
>
> Key finding: the upstream fix (3bfdc63936dd) reveals the real bug is in
> `remove_waiter()` using `current` instead of `waiter->task` in the
> proxy-lock rollback path. The pi_waiters rb_erase path we pursued in
> Phase 3-4 is structurally unreachable in normal control flow.

## Upstream fix analysis (3bfdc63936dd)

The fix changes `remove_waiter()` in 3 places:

| Old code (buggy)               | New code (fixed)                    | Impact                          |
|---------------------------------|-------------------------------------|---------------------------------|
| `raw_spin_lock(&current->pi_lock)` | `raw_spin_lock(&waiter_task->pi_lock)` | 锁正确的 task                |
| `current->pi_blocked_on = NULL` | `waiter_task->pi_blocked_on = NULL` | 清除正确的 PI 状态            |
| `..., current` in adjust_prio_chain | `..., waiter_task` in adjust_prio_chain | chain walk 操作正确的 task |

**Bug mechanism:** When `remove_waiter()` is called from `rt_mutex_start_proxy_lock()` (proxy-lock rollback via `futex_requeue()`), `waiter->task ≠ current`. The old code operates on `current` (the wrong task), causing:
1. `current->pi_blocked_on` cleared (shouldn't be)
2. `waiter_task->pi_blocked_on` NOT cleared (should be → stale pointer)
3. `rt_mutex_adjust_prio_chain(..., current)` operates on wrong task

## Why pi_waiters rb_erase path is DEAD

Static disassembly of `rt_mutex_adjust_prio_chain` (0x81eb65c) proves:

- Guard at 0x81ec0d0 requires `w26=1`
- `w26=1` requires `f_pi_target == (owner->pi_waiters.rb_leftmost - 0x18)` — this is `lock == waiter_struct_pointer`, which is never true in normal flow
- When `w26=0`, `[sp, #8] = 0` (set at 0x81ebaf8), and the guard `cmp [sp,#8], x28` always fails
- Therefore the pi_waiters erase at 0x81ec11c is **structurally unreachable**

Phase 4's crash was NOT from pi_waiters erase. It was from `remove_waiter → tree_entry erase` (0x81ebb4c) under specific heap layout — a one-time偶然, not the designed exploit path.

## Dangling pi_blocked_on hypothesis (PENDING)

The real exploitation primitive may be:

```
remove_waiter() called with current != waiter_task
  → current->pi_blocked_on = NULL (wrong task cleared)
  → waiter_task->pi_blocked_on still points to dequeued waiter struct
  → stale pointer left in kernel
  → later code reads waiter_task->pi_blocked_on → dereferences stale pointer
  → crash / potential write
```

**Verified:**
- remove_waiter is called ONLY from rt_mutex_start_proxy_lock (0x81ed6d8, 0x81eda8c)
- remove_waiter uses `current` (sp_el0) at 0x81eb000, clears `current->pi_blocked_on` at 0x81eb084
- adjust_prio_chain called with `x5 = current` at 0x81eb2b0 (should be waiter_task)

**Pending:**
- Who reads `waiter_task->pi_blocked_on` after remove_waiter returns?
- Which kernel paths consume the stale pointer?
- Can pselect overlay influence the stale pointer's value?

## Dead-end paths (verified, do not retry)

### 1. Consumer waiter tree_entry write (DEAD)
rb_link_node in task_blocks_on_rt_mutex reinitializes rb_right=NULL, rb_left=NULL.
Heap-sprayed values are overwritten before consumer's FUTEX_LOCK_PI runs.

### 2. Requeue waiter tree erase with parent hijack (DEAD)
Guard at 0x81ebb00 (`cmp x9, x28; b.eq skip`) skips rb_erase when waiter is not in the waiter list.

### 3. pi_waiters rb_erase via priority stratification (DEAD)
Guard at 0x81ec0d0 requires w26=1, which needs `lock == waiter_struct_pointer` — never true in normal control flow.
