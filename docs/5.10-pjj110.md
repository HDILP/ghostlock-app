## Why 5.10 needed hand-derived offsets

The Rust extractor (`tools/extract_rs`) requires BTF (`rt_mutex_waiter.pi_tree/wake_state`)
to derive `pselect_waiter_shift` and `struct_fields`. PJJ110's kernel has no BTF, so:

- symbol offsets (`off_init_task` … `off_slide_*`) came from extract_rs (kallsyms recovery) and
  were cross-checked against an independent kallsyms reconstruction (`vmlinux-to-elf`);
- struct offsets came from targeted disassembly of the shipped kernel
  (see `src/core/target.h` comments for the evidence chain).

## pselect_waiter_shift = -2 (frame-derived)

The freed `rt_mutex_waiter` and the pselect `stack_fds` buffer land at the **same**
kernel-stack offset:

```
futex chain:  __arm64_sys_futex(0x90) + do_futex(0x70) + futex_wait_requeue_pi(0x1a0)
              waiter @ sp+0x90  -> depth 0x210
pselect chain: __arm64_sys_pselect6(0xa0) + core_sys_select(0x1c0)
              stack_fds @ sp+0x50 -> depth 0x210
=> waiter == fd_set word 0  =>  shift = -2 (same convention as 6.6)
```

`src/core/fops.c` carries a 5.10 word map under `PSELECT_WORDS_V5_10` (no augment
prio/deadline, no wake_state — those fields do not exist in the 5.10 waiter struct).

## OPPO/QC 5.10 vendor traps (binary-verified, 6.x GKI does NOT have these)

1. **`BUG_ON(rt_mutex_top_waiter(lock)->lock != lock)`** — `brk #0x800` traps in
   `remove_waiter()` (0x1eb540 entry, 0x1eb5bc top-waiter branch) and in
   `mark_wakeup_next_waiter()` (0x1ea138). The fd_set overlay must NOT overwrite
   `waiter->lock` (+0x38) — keep the original `pi_mutex` pointer intact or the
   kernel panics before any rb op runs (fix: `fops.c` word 9 removed).
   `task_blocks_on_rt_mutex()` rewrites waiter->task/lock to real values on
   enqueue, which is what lets the check pass on the requeue path.
2. **`mm_struct` is 0x3c0** (verified from `mm_init` →
   `kmem_cache_create_usercopy` size arg), not 0x500 (6.x GKI). KernelSnitch's
   futex-hash brute force strides by `MM_STRUCT_SZ`; with 0x500 it misses every
   real slab object and the mm leak fails (fix: `common.h` `MM_STRUCT_SZ 0x3c0`).
3. **rb_insert_color NULL-grandparent panic**: when `task_blocks_on_rt_mutex()`
   re-inserts the consumer waiter under the stale fake node, a fake
   `tree_entry.__rb_parent_color` of 0 is seen as RED-with-no-parent and the
   insert loop dereferences a NULL grandparent. Setting it to 1 (RB_BLACK) makes
   the loop break.
4. KernelSnitch mm leak is a **futex-hash side channel**, not perf: it brute
   forces `mm_struct` candidates in the direct-map range by correlating
   `futex_hash(futex_addr, mm)` bucket collisions.

## Write primitive analysis — pi_waiters path (2026-08-17, CONFIRMED)

### Core finding: waiter enters owner's pi_waiters via priority boost

**sched_setattr(nice=-10)** on the waiter thread before FUTEX_WAIT_REQUEUE_PI causes
rt_mutex_adjust_prio_chain during requeue to add the waiter to the owner's pi_waiters
tree via pi_tree_entry. This was confirmed by:

1. **Crash diagnostic** (2026-08-17): Setting pi_tree_entry.__rb_parent_color =
   0xdead000000000001 caused a panic. The chain walk dereferenced the poisoned
   parent pointer. This proves the waiter IS in the pi_waiters tree and the chain
   walk DOES read pi_tree_entry.__rb_parent_color.

2. **Phase 4 crash** (2026-08-17): Priority stratification (consumer=100, waiter=110,
   owner=120) caused a crash on the second round. The guard at 0x81ec0d0 passed,
   and rb_erase fired on the corrupted pi_tree_entry.

### Guard condition (0x81ec0cc-0x81ec0d4)

```asm
0x81ec0cc: ldr x9, [sp, #8]     ; x9 = lock->wait_list.rb_leftmost
0x81ec0d0: cmp x9, x28          ; x28 = task->pi_blocked_on
0x81ec0d4: b.ne 0x81ec814       ; if leftmost ≠ pi_blocked_on → SKIP
```

**C semantic**: `if (lock->wait_list.rb_leftmost != task->pi_blocked_on) goto skip;`

This is an **is_top_waiter check**: the pi_waiters rb_erase only fires when the
waiter being processed is the leftmost (highest-priority) node in the waiter tree.

**Why Phase 3 failed**: Both waiter and consumer were nice=-20 (prio 100). Requeued
waiter was leftmost (inserted first, same priority). Consumer's pi_blocked_on pointed
to its own waiter (not the leftmost). Guard: leftmost(requeued) ≠ pi_blocked_on(consumer) → skip.

**Why Phase 4 worked**: Priority stratification:
- Consumer nice=-20 (prio 100) → leftmost in waiter tree
- Requeued waiter nice=-10 (prio 110) → in pi_waiters (110 < owner's 120)
- Guard: leftmost(consumer@100) == pi_blocked_on(consumer) → PASS

### rb_erase write path (0x81ab07d4-0x81ab07f4)

```asm
0x81ab07d4: ldr x9, [x0]           ; x9 = node->__rb_parent_color
0x81ab07d8: ands x10, x9, #-4      ; x10 = parent = value & ~3
0x81ab07dc: b.eq 0x81ab08b0        ; parent==0 → root path
0x81ab07e0: mov x11, x10            ; x11 = parent
0x81ab07e4: ldr x12, [x11, #0x10]! ; x12 = parent->rb_left, x11 = &parent->rb_left
0x81ab07e8: sub x13, x11, #8       ; x13 = &parent->rb_right
0x81ab07ec: cmp x12, x0            ; parent->rb_left == node?
0x81ab07f0: csel x11, x11, x13, eq ; if eq → write to rb_left, else → rb_right
0x81ab07f4: str x8, [x11]          ; WRITE: *target = replacement
```

With `__rb_parent_color = (target-8)|1`:
- parent = target-8
- `parent->rb_right` is at address `target`
- `parent->rb_left` is at address `target+8`
- If `*(target+8) ≠ node` → writes to `target` (SELinux enforcing)

Replacement value = node's rb_right (which we set to 0 via pselect word 6).
Result: **write-0 to target**.

### Priority stratification scheme

```
consumer   nice=-20  prio=100  → leftmost in waiter tree → guard passes
waiter     nice=-10  prio=110  → enters pi_waiters (110 < 120)
owner      nice=0    prio=120  → lowest
```

## Dead-end paths (verified, do not retry)

### 1. Consumer waiter tree_entry write (DEAD)

rb_link_node in task_blocks_on_rt_mutex reinitializes rb_right=NULL, rb_left=NULL.
Heap-sprayed values are overwritten before consumer's FUTEX_LOCK_PI runs.

### 2. Requeue waiter tree erase with parent hijack (DEAD)

Guard at 0x81ebb00 (`cmp x9, x28; b.eq skip`) skips rb_erase when waiter is not
in the waiter list (only in tree). Even when it fires, root is lock->waiters, not target.

### 3. NFDS=128 pi_waiters erase without priority boost (DEAD)

Requeued waiter not in pi_waiters tree (no priority difference). Guard skips erase.
Confirmed by Phase 3: stable, no crash, no write.
