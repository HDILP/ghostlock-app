# 5.10 Port — OPPO Reno11 Pro (PJJ110)

> Experimental first 5.10 port of the GhostLock (CVE-2026-43499) exploit family.
> Status: **offsets verified from the actual kernel image; on-device runtime bring-up
> in progress** — fixed so far: offsets-table include, OPPO `BUG_ON` waiter->lock
> checks, `MM_STRUCT_SZ` (0x3c0), fake tree node color. Remaining blocker: kernel
> panic right after `pselect pre-select` (diagnostic `punch_seq` markers landed in
> commit 88737ac).

## Why 5.10 needed hand-derived offsets

The Rust extractor (`tools/extract_rs`) requires BTF (`rt_mutex_waiter.pi_tree/wake_state`)
to derive `pselect_waiter_shift` and `struct_fields`. PJJ110's kernel has no BTF, so:

- symbol offsets (`off_init_task` … `off_slide_*`) came from extract_rs (kallsyms recovery) and
  were cross-checked against an independent kallsyms reconstruction (`vmlinux-to-elf`);
- struct offsets came from targeted disassembly of the shipped kernel
  (see `src/core/target.h` comments for the evidence chain).

## pselect_waiter_shift = -2 (frame-derived)

The freed `rt_mutex_waiter` and the pselect `stack_fds` buffer land at the **same**
kernel-stack offset:

```
futex chain:  __arm64_sys_futex(0x90) + do_futex(0x70) + futex_wait_requeue_pi(0x1a0)
              waiter @ sp+0x90  -> depth 0x210
pselect chain: __arm64_sys_pselect6(0xa0) + core_sys_select(0x1c0)
              stack_fds @ sp+0x50 -> depth 0x210
=> waiter == fd_set word 0  =>  shift = -2 (same convention as 6.6)
```

`src/core/fops.c` carries a 5.10 word map under `PSELECT_WORDS_V5_10` (no augment
prio/deadline, no wake_state — those fields do not exist in the 5.10 waiter struct).

## OPPO/QC 5.10 vendor traps (binary-verified, 6.x GKI does NOT have these)

1. **`BUG_ON(rt_mutex_top_waiter(lock)->lock != lock)`** — `brk #0x800` traps in
   `remove_waiter()` (0x1eb540 entry, 0x1eb5bc top-waiter branch) and in
   `mark_wakeup_next_waiter()` (0x1ea138). The fd_set overlay must NOT overwrite
   `waiter->lock` (+0x38) — keep the original `pi_mutex` pointer intact or the
   kernel panics before any rb op runs (fix: `fops.c` word 9 removed).
   `task_blocks_on_rt_mutex()` rewrites waiter->task/lock to real values on
   enqueue, which is what lets the check pass on the requeue path.
2. **`mm_struct` is 0x3c0** (verified from `mm_init` →
   `kmem_cache_create_usercopy` size arg), not 0x500 (6.x GKI). KernelSnitch's
   futex-hash brute force strides by `MM_STRUCT_SZ`; with 0x500 it misses every
   real slab object and the mm leak fails (fix: `common.h` `MM_STRUCT_SZ 0x3c0`).
3. **rb_insert_color NULL-grandparent panic**: when `task_blocks_on_rt_mutex()`
   re-inserts the consumer waiter under the stale fake node, a fake
   `tree_entry.__rb_parent_color` of 0 is seen as RED-with-no-parent and the
   insert loop dereferences a NULL grandparent. Setting it to 1 (RB_BLACK) makes
   the loop break. (Simulated + verified; still panicking on device as of
   88737ac — see punch_seq diagnostics.)
4. KernelSnitch mm leak is a **futex-hash side channel**, not perf: it brute
   forces `mm_struct` candidates in the direct-map range by correlating
   `futex_hash(futex_addr, mm)` bucket collisions.

## Bring-up log (2026-08-17)

- `648085f` — known_offsets table was missing the 5.10 entry include
  (offsets.h had `STRUCT_OFFSETS_5_10` but no `#include` line) → "no offsets
  for kernel" on device.
- `b2cc201` — stop overwriting `waiter->lock` in the fd_set words (trap #1).
- `c5873c1` — `MM_STRUCT_SZ` 0x3c0 (trap #2); mm leak went from 8/8 failures to
  success.
- `62eb4e9` — fake `tree_pc` = 1 / RB_BLACK (trap #3); printed `in0=1` confirms
  the word lands, but device still panics at `pselect pre-select`.
- `88737ac` — `punch_seq` fsync markers around each consumer step
  (sched/lock/unlock) to pinpoint the panicking syscall.

## Notes / risks

- No BTF means the extractor's `--register` will emit a partial table; always hand-verify
  `struct_fields` on 5.10 builds.
- The write primitive relies on 5.10's plain `rb_erase` (6.x uses `rb_erase_cached`) —
  first runtime test may need primitive tuning.
- ~~Boot-animation two-phase strategy (cache KASLR via SLIDE, then DIRECT)~~ **NOT needed
  for this fork**: no `tgkill` calls anywhere and all write targets go through the
  physmap alias (`p0_data_alias`), so no KASLR leak is required at all. Run anytime.
  (Original XDA/酷安 strategy applies to the upstream tgkill-based SLIDE stage.)
- MSYS2 builds: use `-Wl,-dynamic-linker,//system/bin/linker64` (double slash) or the ELF
  `.interp` ends up as a Windows path and the binary dies with ENOENT.
