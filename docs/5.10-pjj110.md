# 5.10 Port — OPPO Reno11 Pro (PJJ110)

> Experimental first 5.10 port of the GhostLock (CVE-2026-43499) exploit family.
> Status: **write-0 primitive NOT working — all tested paths are dead ends** (as of 2026-08-17).
> The pselect overlay covers `tree_entry` (+0x00..+0x17); the consumer
> runs `FUTEX_LOCK_PI` directly (sched_setattr skipped). Route completes
> cleanly (step=0), device does not crash, but no memory write reaches
> the target. See "Write primitive analysis" for the three dead-end paths
> and the root causes.

## Why 5.10 needed hand-derived offsets

The Rust extractor (`tools/extract_rs`) requires BTF (`rt_mutex_waiter.pi_tree/wake_state`)
to derive `pselect_waiter_shift` and `struct_fields`. PJJ110's kernel has no BTF, so:

- symbol offsets (`off_init_task` … `off_slide_*`) came from extract_rs (kallsyms recovery) and
  were cross-checked against an independent kallsyms reconstruction (`vmlinux-to-elf`);
- struct offsets came from targeted disassembly of the shipped kernel
  (see `src/core/target.h` comments for the evidence chain).

## pselect_waiter_shift = -2 (frame-derived)

The freed `rt_mutex_waiter` and the pselect `stack_fds` buffer land at the **same**
kernel-stack offset:

```
futex chain:  __arm64_sys_futex(0x90) + do_futex(0x70) + futex_wait_requeue_pi(0x1a0)
              waiter @ sp+0x90  -> depth 0x210
pselect chain: __arm64_sys_pselect6(0xa0) + core_sys_select(0x1c0)
              stack_fds @ sp+0x50 -> depth 0x210
=> waiter == fd_set word 0  =>  shift = -2 (same convention as 6.6)
```

`src/core/fops.c` carries a 5.10 word map under `PSELECT_WORDS_V5_10` (no augment
prio/deadline, no wake_state — those fields do not exist in the 5.10 waiter struct).

## OPPO/QC 5.10 vendor traps (binary-verified, 6.x GKI does NOT have these)

1. **`BUG_ON(rt_mutex_top_waiter(lock)->lock != lock)`** — `brk #0x800` traps in
   `remove_waiter()` (0x1eb540 entry, 0x1eb5bc top-waiter branch) and in
   `mark_wakeup_next_waiter()` (0x1ea138). The fd_set overlay must NOT overwrite
   `waiter->lock` (+0x38) — keep the original `pi_mutex` pointer intact or the
   kernel panics before any rb op runs (fix: `fops.c` word 9 removed).
   `task_blocks_on_rt_mutex()` rewrites waiter->task/lock to real values on
   enqueue, which is what lets the check pass on the requeue path.
2. **`mm_struct` is 0x3c0** (verified from `mm_init` →
   `kmem_cache_create_usercopy` size arg), not 0x500 (6.x GKI). KernelSnitch's
   futex-hash brute force strides by `MM_STRUCT_SZ`; with 0x500 it misses every
   real slab object and the mm leak fails (fix: `common.h` `MM_STRUCT_SZ 0x3c0`).
3. **rb_insert_color NULL-grandparent panic**: when `task_blocks_on_rt_mutex()`
   re-inserts the consumer waiter under the stale fake node, a fake
   `tree_entry.__rb_parent_color` of 0 is seen as RED-with-no-parent and the
   insert loop dereferences a NULL grandparent. Setting it to 1 (RB_BLACK) makes
   the loop break.
4. KernelSnitch mm leak is a **futex-hash side channel**, not perf: it brute
   forces `mm_struct` candidates in the direct-map range by correlating
   `futex_hash(futex_addr, mm)` bucket collisions.

## Write primitive analysis (2026-08-17)

Three write-0 paths were tested. All are dead ends.

### Path 1: Consumer waiter C tree_entry write (DEAD END)

**Theory**: Set `W->rb_right = target` in heap spray. When consumer waiter C (RED
leaf, right child of W due to prio tie at 120) is erased on FUTEX_LOCK_PI timeout,
`__rb_change_child(W, NULL, parent_of_C)` writes `W->rb_right = C->rb_right` (NULL)
to target.

**Why it fails**: `task_blocks_on_rt_mutex()` inserts C into the lock's waiter tree
via `rb_link_node()`, which reinitializes `tree_entry.rb_right = NULL` and
`tree_entry.rb_left = NULL`. The heap-sprayed `W->rb_right = target` is overwritten
before the consumer's FUTEX_LOCK_PI even runs. The erase writes to the stack
(waiter+0x08), not to our target.

**Evidence**: `W->rb_right = target` set in heap spray (`util.c`), route completes
(step=0), but SELinux remains enforcing after 15 rounds.

### Path 2: Requeue waiter tree erase with __rb_parent_color hijack (DEAD END)

**Theory**: Set `tree_entry.__rb_parent_color = (target-8)|1` in the pselect copy.
The requeue `rb_erase` in `rt_mutex_adjust_prio_chain` reads parent = target-8,
compares `parent->rb_left` with node (mismatch), then writes `node->rb_right` (=0)
to `&parent->rb_right` = target.

**Why it fails**: The requeue `rb_erase` call at `0x81ebb4c` is inside a conditional
block gated by `cmp x9, x28; b.eq skip`. If the waiter is not in the waiter list
(only in the tree), the condition fires and the rb_erase is skipped entirely. Even
when it does fire, the tree root passed is `lock->waiters` (the old lock's structure),
not our target. Disassembly shows:
```
0x81ebb00:  cmp x9, x28       ; x9 == waiter?
0x81ebb04:  b.eq 0x81ebb64    ; YES → skip rb_erase entirely
...
0x81ebb4c:  bl rb_erase        ; x0=waiter, x1=x27+8 (lock->waiters)
```

**Evidence**: `in0=ffffff8002a683c1` confirms `(target-8)|1` was placed, route
completes (step=0), no crash, but SELinux still enforcing.

### Path 3: pi_waiters tree erase via NFDS=128 (DEAD END)

**Theory**: Expand NFDS to 128 to cover pi_tree_entry (+0x18..+0x2f). Set
`pi_tree_entry.__rb_parent_color = target-8`. The pi_waiters `rb_erase` in
`rt_mutex_adjust_prio_chain` would write through the parent pointer.

**Why it fails**: The requeued waiter W is NOT in the owner's pi_waiters tree.
`FUTEX_WAIT_REQUEUE_PI` adds the waiter to the lock's waiter tree (via tree_entry),
but NOT to the owner's pi_waiters tree (via pi_tree_entry). The two pi_waiters
erase calls at `0x81ec11c` and `0x81ec700` have a guard `cmp x9, x28; b.ne skip`
that skips the erase when the waiter is not in the tree.

**Evidence**: NFDS=128 tested, no crash (pi_tree_entry corruption handled
gracefully), but SELinux still enforcing. All 15 rounds complete cleanly.

### Root cause summary

The fundamental issue is **tree_entry reinitialization by rb_link_node**. Every
insertion path (`task_blocks_on_rt_mutex`, `rt_mutex_enqueue`) calls
`rb_link_node()` which sets `rb_right=NULL, rb_left=NULL`. The pselect copy values
are overwritten before any erase can consume them.

Additionally, the requeued waiter W is only in the **lock's waiter tree** (via
tree_entry), NOT in the **owner's pi_waiters tree** (via pi_tree_entry). This
eliminates the pi_tree path entirely.

### Next steps

1. **RAMDUMP**: Use Qualcomm crash dump tools to capture register state during
   the requeue rb_erase. Confirm which branch is taken and what root/address
   is actually written to.
2. **Object lifecycle mapping**: Trace which objects land in which trees at which
   points, and which removal sites are actually reachable with controlled
   parameters.
3. **Alternative primitive**: Consider UAF object reuse, different futex
   operations, or non-rb-tree write paths.

## Bring-up log (2026-08-17)

- `648085f` — known_offsets table was missing the 5.10 entry include
  (offsets.h had `STRUCT_OFFSETS_5_10` but no `#include` line) → "no offsets
  for kernel" on device.
- `b2cc201` — stop overwriting `waiter->lock` in the fd_set words (trap #1).
- `c5873c1` — `MM_STRUCT_SZ` 0x3c0 (trap #2); mm leak went from 8/8 failures to
  success.
- `62eb4e9` — fake `tree_pc` = 1 / RB_BLACK (trap #3); printed `in0=1` confirms
  the word lands, but device still panics at `pselect pre-select`.
- `88737ac` — `punch_seq` fsync markers around each consumer step
  (sched/lock/unlock) to pinpoint the panicking syscall.
- NFDS 320→128→64 progression to avoid vendor traps (see trap descriptions above).
- `16b917d` — skip sched_setattr in consumer, go straight to FUTEX_LOCK_PI.
- `67ff2ed` — wire write-0 primitive: `W->rb_right = target` in heap spray
  (`util.c`); remove `consumer_success > 0` from success check (`main.c` + `fops.c`).
- `223c384` — NFDS 64→128 diagnostic: add pi_tree_entry entries to 5.10 map,
  set `pi_parent = target-8`. No crash but no write either.
- `c70da3c` — requeue rb_erase parent hijack: `tree_pc = (target-8)|1` in pselect
  copy. Route completes (step=0) but SELinux still enforcing.
- **Conclusion (2026-08-17)**: Three write-0 paths tested, all dead ends.
  `rb_link_node` reinitializes tree_entry on insertion; requeued waiter not in
  pi_waiters tree. Need RAMDUMP or alternative primitive.

## Notes / risks

- No BTF means the extractor's `--register` will emit a partial table; always hand-verify
  `struct_fields` on 5.10 builds.
- **Write-0 primitive NOT working** (2026-08-17): All three tested paths are dead
  ends. See "Write primitive analysis" section above. The core issue is
  `rb_link_node` reinitializing `tree_entry` on insertion, and the requeued
  waiter being absent from the owner's pi_waiters tree.
- ~~Boot-animation two-phase strategy (cache KASLR via SLIDE, then DIRECT)~~ **NOT needed
  for this fork**: no `tgkill` calls anywhere and all write targets go through the
  physmap alias (`p0_data_alias`), so no KASLR leak is required at all. Run anytime.
  (Original XDA/酷安 strategy applies to the upstream tgkill-based SLIDE stage.)
- MSYS2 builds: use `-Wl,-dynamic-linker,//system/bin/linker64` (double slash) or the ELF
  `.interp` ends up as a Windows path and the binary dies with ENOENT.
