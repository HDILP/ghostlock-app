## 漏洞分析

### upstream fix (3bfdc63936dd)

| 旧代码 (有 bug)                   | 新代码 (修复后)                  | 影响                          |
|----------------------------------|--------------------------------|-------------------------------|
| `raw_spin_lock(&current->pi_lock)` | `raw_spin_lock(&waiter_task->pi_lock)` | 锁正确的 task |
| `current->pi_blocked_on = NULL` | `waiter_task->pi_blocked_on = NULL` | 清除正确的 PI 状态 |
| `..., current` in adjust_prio_chain | `..., waiter_task` | chain walk 用正确的 task |

### 已证明不可行的路径

#### 1. pi_waiters rb_erase (DEAD)
- Guard at 0x81ec0d0 要求 `w26=1`
- `w26=1` 需要 `lock == waiter_struct_pointer`，正常控制流下永远不成立

#### 2. NFDS=320 pselect 覆写 — BUG_ON bypass
- vendor 在 `task_blocks_on_rt_mutex` (0x1ea860) 添加了 `BUG_ON(left_child->lock != waiter)` (3 处 brk #0x800)
- NFDS=128 copy 范围 = waiter+0x00..+0x2f → lock 字段(+0x38)不在范围内 → BUG_ON 不触发
- NFDS=320 copy 范围 = waiter+0x00..+0x4f → lock 字段在范围内 → **panic**
- Bypass 方案（设置 lock=waiter 自引用）理论可行，但前置条件（泄漏 waiter 内核地址）未解决

#### 3. dangling pi_blocked_on UAF (DEAD)
- 理论：remove_waiter 清除 current 而非 waiter_task → waiter_task->pi_blocked_on 悬垂
- **实际情况**：`try_to_take_rt_mutex` 在 waiter_task 成功获取锁时清除其 `pi_blocked_on`
- Phase 6 实验验证：15/15 稳定无 crash

#### 4. KGSL GPU exploit (DEAD)
- CVE-2025-21479 exploit 在设备上运行失败

## write-0 原语定性 (2026-08-20)

### 机制

```
rb_erase(C)
  → parent = C->__rb_parent_color & ~3 = W (requeued waiter on kernel stack)
  → C is W's right child
  → str x8, [x11]  where x11 = &parent->rb_right = &W->rb_right
  → writes NULL to W + 0x08
```

**写入目标**: W + 0x08 (kernel stack address)
**写入值**: NULL (from C->rb_right, set by rb_link_node)

### 关键澄清

- W 是 requeued waiter，位于 **main thread 内核栈** 上
- W 的地址由 KASLR 随机化，不可预测
- W + 0x08 是内核栈地址，**不是** selinux_enforcing 或任何内核 .data 地址
- 堆喷的 fake waiter W0 有 `rb_right = target`（= selinux_enforcing），但 W0 **不在** f_pi_target 的 waiter tree 中，消费者 C 不会成为 W0 的子节点
- pselect overlay 修改了 W 的 tree_entry 字段（在内核栈上），但 rb_erase 写的是 `&W->rb_right`（内核栈），不是 `*W->rb_right`（target）

### Primitive 能力边界

| 能力 | 状态 |
|------|------|
| kernel-stack write-0 | ✅ 已验证 (15/15 stable) |
| kernel address disclosure | ✅ perf SP leak confirmed |
| arbitrary kernel write | ❌ 无法达到 |
| write to kernel data (.data/.bss) | ❌ 无法到达 |
| privilege escalation | ❌ 无法实现 |

### 结论

> GhostLock 在这个特定 PJJ110 vendor 5.10.226 内核上，可以稳定构造 kernel-stack corruption + address disclosure，但现有 primitive 无法闭合为 arbitrary kernel write，因此目前没有证明 LPE。

## perf SP Leak 实验 (2026-08-20)

### 结果

通过 perf_event_open (PERF_SAMPLE_REGS_INTR) 在 FUTEX_WAIT_REQUEUE_PI 期间收集内核态寄存器快照。

- **SP 聚类成功**: Round 8 有 22/43 samples 共享同一个 SP
- **KASLR 基地址确认**: 所有 kernel SP 在 `0xffffffc0...` 范围
- **W 定位**: W = sample_SP + 0x90 (binary invariant, SP write-set audit 确认)

### SP Write-Set Audit

futex_wait_requeue_pi (2932 bytes) 全函数扫描：
- SP 修改指令仅 2 处：prologue (`sub sp, sp, #0x1a0`) + epilogue (`add sp, sp, #0x1a0`)
- 函数体内无任何 SP 修改
- Δ = +0x90 是 **binary invariant**

### 局限性

perf SP leak 解决了 "Where?"（知道了 W 的地址），但没有解决 "Can I choose Where?"（不能选择写入目标）。W + 0x08 仍然是内核栈地址，不是内核数据地址。

### NFDS 覆盖分析

| NFDS | words/set | Copy range | task(+0x30) | lock(+0x38) |
|------|-----------|------------|-------------|-------------|
| 64   | 1         | +0x00..0x07 | ✗ | ✗ |
| 128  | 2         | +0x00..0x0f | ✗ | ✗ |
| 192  | 3         | +0x00..0x17 | ✓ | ✓ |
| 256  | 4         | +0x00..0x1f | ✓ | ✓ |
| 320  | 5         | +0x00..0x27 | ✓ | ✓ |

NFDS=192+ 覆盖 task 和 lock 字段。BUG_ON 检查 leftmost waiter 的 lock 字段。

### 64-bit Store 安全性

selinux_enforcing @ 0xaa683c8 (int, 4 bytes)。
相邻 136 字节 gap 到下一个 symbol → 几乎确定是 padding。
sel_write_enforce 使用 STRB (byte store) → 语义上是 bool。
**结论**: 8-byte zero store 的邻接副作用可接受。

## Dead-end paths (勿重复尝试)

1. **pi_waiters rb_erase** — guard w26=0 恒假，结构性不可达
2. **dangling pi_blocked_on** — try_to_take_rt_mutex 清除
3. **KGSL GPU r/w** — 漏洞已修补
4. **consumer tree_entry write** — rb_link_node 重置 rb_right/rb_left
5. **requeue waiter tree erase** — list guard 守卫
6. **NFDS=320 BUG_ON bypass** — 前置条件未满足，且 write-0 本身不能到达内核数据
