# 5.10 BUG_ON Bypass — vendor rt_mutex check in task_blocks_on_rt_mutex

> 2026-08-19 实测分析。基于 PJJ110 内核 5.10.226 反汇编。

## 问题

vendor 在 `task_blocks_on_rt_mutex`（0x1ea860）中添加了 `BUG_ON(root->lock != lock)` 检查（3 处 brk #0x800）。
当 waiter 的 lock 字段被 pselect 覆写为非 lock 值时，BUG_ON 触发 panic，阻止了 NFDS=320 exploit 路径。

## BUG_ON 精确位置

### BUG_ON #1 — waiter tree integrity check（0x1eaa34）

```
task_blocks_on_rt_mutex:
  x19 = waiter (第一个参数)
  x22 = lock (第二个参数)
  x23 = task (第三个参数)

  0x1eaa28: ldr x8, [x19, #0x10]    // x8 = waiter->tree_node.rb_left
  0x1eaa2c: cbz x8, #0x1eaa3c       // if NULL → skip (正常路径)
  0x1eaa30: ldr x9, [x8, #0x38]    // x9 = left_child->lock
  0x1eaa34: cmp x9, x19             // cmp left_child->lock, waiter
  0x1eaa38: b.ne #0x1eaea4          // BUG_ON: if not equal → BRK #0x800
  0x1eaa3c: ...
```

**语义**：如果 waiter tree 有左子节点，左子节点的 lock 字段必须等于 waiter 本身。
这是 tree 一致性检查：所有在同一 lock 的 waiter tree 中的 waiter 应该有相同的 lock 指针。

### BUG_ON #2 — pi_waiters check（0x1eaea0/0x1eaea4）

```
  0x1eae94: ldr x8, [x19, #0x10]    // waiter->tree_node.rb_left
  0x1eae98: cbnz x8, #0x1eaa30      // if non-NULL → go to check #1
  0x1eae9c: b #0x1eaa3c             // else → skip
  0x1eaea0: brk #0x800              // BUG_ON (debug)
  0x1eaea4: brk #0x800              // BUG_ON (unreachable)
```

这两个 BUG_ON 在同一检查路径上，逻辑相同。

## 为什么 NFDS=128 不触发

```
NFDS=128 → words_per_set = 2
  copy range: waiter+0x00 → waiter+0x2f (16 bytes × 2 sets = 32 bytes)
  
  waiter layout:
    +0x00..+0x17: tree_entry (被 copy 覆写) ✓
    +0x18..+0x2f: pi_tree_entry (被 copy 覆写) ✓
    +0x30..+0x37: task (不在 copy 范围内) ✗
    +0x38..+0x3f: lock (不在 copy 范围内) ✗
```

**waiter+0x38（lock 字段）不在 NFDS=128 的 copy 范围内**，所以：
- waiter->lock 保持内核初始化的原始值（正确的 rt_mutex 指针）
- BUG_ON 检查永远不会触发（因为 left_child->lock 始终是正确的 lock）

## NFDS=320 Bypass 方案

### 核心思路

```
NFDS=320 → words_per_set = 5 (320/64=5)
  copy range: waiter+0x00 → waiter+0x4f (40 bytes)
  
  waiter layout:
    +0x00..+0x17: tree_entry     ← 被 pselect 控制
    +0x18..+0x2f: pi_tree_entry  ← 被 pselect 控制
    +0x30..+0x37: task           ← 被 pselect 控制
    +0x38..+0x3f: lock           ← 被 pselect 控制 ← 关键！
```

**fd_set word 7** → waiter+0x38（lock 字段）

**Bypass**：设置 word 7 = waiter 的内核地址 → `waiter->lock = waiter`（自引用）

### BUG_ON 验证

```
BUG_ON #1:
  x8 = waiter->tree_node.rb_left  (由 word 0-2 控制)
  if x8 != NULL:
    x9 = left_child->lock          (由 word 7 控制，如果 left_child = waiter)
    cmp x9, waiter                 → 相等 → 不触发 BUG_ON ✓

实际场景：left_child 是 fake waiter
  fake_waiter->lock = waiter 的地址
  → BUG_ON 通过 ✓
```

### fd_set word 布局（NFDS=320）

| fd_set word | waiter offset | field | 需要的值 |
|-------------|---------------|-------|----------|
| 0 | +0x00 | tree_entry.__rb_parent_color | (target-8)\|1 |
| 1 | +0x08 | tree_entry.rb_right | 0 (write-0 primitive) |
| 2 | +0x10 | tree_entry.rb_left | 0 |
| 3 | +0x18 | pi_tree_entry.__rb_parent_color | (target-8)\|1 |
| 4 | +0x20 | pi_tree_entry.rb_right | 0 |
| 5 | +0x28 | pi_tree_entry.rb_left | 0 |
| 6 | +0x30 | task | INIT_TASK (保持默认) |
| 7 | +0x38 | lock | **waiter 的内核地址** ← Bypass 关键 |

### 前置条件

需要泄漏 waiter 的内核地址（KASLR-dependent）：
- 当前 exploit 已有 `perf_find_task()` 泄漏 child_task
- 需要增加 waiter 的泄漏（通过 futex collision 或其他方式）
- 或者：waiter 地址可以通过其他方式推导

### 其他 Bypass 路径

#### 路径 2：修改 BUG_ON 本身（需要 W1/W2）
- 将 0x1eaa34 处的 `b.ne` 改为 `nop`
- 需要先有 kernel write primitive
- 更安全但更复杂

#### 路径 3：利用 BUG_ON 前的 NULL 检查
- BUG_ON 在 `cbz x8`（NULL 检查）之后
- 如果 waiter->tree_node.rb_left == NULL → 直接跳过 BUG_ON
- 需要确保 pselect 不覆写 tree_node.rb_left（NFDS=128 已满足）
- 但 NFDS=128 无法覆写 lock → 这是死路

#### 路径 4：find another code path
- BUG_ON 只在 task_blocks_on_rt_mutex 中
- 如果能触发 rb_erase 而不经过 PI chain walk → 无 BUG_ON
- 但 exploit 依赖 PI chain walk 触发 rb_erase

## 实现步骤

1. **泄漏 waiter 地址**
   - 在 waiter_thread 中增加地址泄漏
   - 可用方法：futex collision 的 mm_struct 泄漏

2. **修改 common.h**
   - `#define PSELECT_ROUTE_NFDS 320`

3. **修改 fops.c — prepare_pselect_fdsets**
   - 增加 word 7: `{7, waiter_kernel_addr, "lock"}`
   - 确保 word 6 保持 INIT_TASK

4. **修改 target.h**
   - 增加 `#define FAKE_WAITER_LOCK_SELF 1` 启用 bypass

5. **修改 util.c — prepare_skb_payload**
   - 确保 fake waiter 的 lock 字段 = waiter 地址

6. **测试验证**
   - Phase 0-3 稳定性
   - BUG_ON 不触发
   - 写原语正常工作

## 风险评估

| 风险 | 严重性 | 缓解 |
|------|--------|------|
| waiter 地址泄漏失败 | 高 | 多次重试 + 备用泄漏方法 |
| waiter->lock=waiter 导致其他 crash | 中 | 仅影响 PI chain walk，不影响 lock acquisition |
| copy 范围扩大导致其他字段被覆写 | 低 | 严格控制每个 word 的值 |
| NFDS=320 超出系统限制 | 低 | fd limit 通常 1024，320 远低于限制 |

## 附录：NFDS=128 write-0 word 3 问题 (2026-08-19 发现)

NFDS=128 时 pselect copy 窗口覆盖 waiter+0x00..+0x2f，其中 word 3 映射到 waiter+0x08 (rb_right)。

原始代码设 word 3=0，这在 NFDS=64 时不影响 target（word 3 映射到 waiter+0x20），但 NFDS=128 时覆盖了 skb 中设置的 target 值。

修复：`pselect_child_node ? 0 : target`
- leaf=1 (write-0): word 3=0 → rb_erase 写 0
- leaf=0 (write-N): word 3=target → rb_erase 写 target

修复后 write-0 触发 (calls=1) 但未命中 selinux_enforcing (enforce=1)。目标地址需进一步调查。
